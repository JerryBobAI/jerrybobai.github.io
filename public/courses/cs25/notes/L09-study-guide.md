## 分节要点(带时间锚点)

### 一、为什么要关心推理：从成本中心到收入中心

- 训练虽酷，但从商业视角是成本中心：钱进去、权重出来，而权重像「装软件的 CD」一样难以直接卖钱；必须围绕模型建系统才能产生营收，营收再反哺训练——连只管签支票的投资人也要沿途看到营收([0:00])
- 预训练只有少数组织在做(如同只有少数厂商能造芯片，多数人建在其上)，推理却无处不在且越来越多；连训练自己都越来越依赖高效推理：RL 后训练要生成输出、与世界交互再回灌权重，这部分 flops 量级可能已超过预训练——连训练负责人都得关心推理([0:02])
- 「无聊的基础设施」正在闷声发财：Sean Wang 发推称 AI infra 圈都在变富——不是性感 AI 研究，是无聊 infra；Modal 融资是注脚；自动研究(auto research)同样能用在这种「无聊」的推理加速上([0:03])
- 推理横跨全栈：既要懂应用(拿来做啥)，也要懂线性代数与 CUDA 模板/layout 代数，还要懂电子、发热与散热——真正全栈工程师的好战场；而且一大波推理需求正在到来，替别人高效消化这些需求是大机会([0:04])
- 讲者 Charles Frye：UC Berkeley 博士(神经网络优化方向，此前做精神药理学与神经生物学研究)，经 Weights & Biases、Full Stack Deep Learning 教过数千人整条 AI 应用栈；在 Modal 做推理约两年，与数百到数千 GPU 规模的头部团队合作，且乐于公开这些经验——「让世界上有更多推理」；本讲是高速世界巡游：应用→工作负载→模型与引擎→硬件→部署→可观测性→性能优化→未来([0:06])

### 二、三类应用原型与工作负载的定义语言

- 原型一 chatbot plus：ChatGPT 与 Claude Code——真人在另一端，按人类反应时间与延迟容忍行事；且不只「聊天」，还会用文本输出替用户操控其他计算机系统([0:07])
- 原型二 background agent(Devin、Resolve、Ramp 的 Inspect、OpenClaw 等，此处口播转写含混、按可辨识名称修正)：人交代完任务就去开会、并不等结果——prompt 里最重要的 token 常由人亲自写，但延迟约束放宽到秒/分/小时级；原型三 data processor(如 Reducto——为 Jail 项目索引了 Epstein 的邮件、把它变成邮件接口的那家)：处理 PDF 等非结构化数据抽取结构，下游是存储/数据库，高吞吐、高延迟容忍、写入呈突发([0:11])
- 工程师与应用方的交接点是工作负载定义：用 SLA/SLO 表达失败率、速度与成本；给客户做咨询时把工作负载问清楚太难，于是有了 LLM Engineer's Almanac 里的「填空式」模板(选模型、定延迟与吞吐约束)，把原本艰难的对话变短([0:12])
- 两个难缠的工作负载参数：QPS 由用户控制、难预测，峰均比越高越难伺候，季节性要趁早摸清；输入/输出 token 数里输出长度最难——何时吐 end-of-text 由模型决定，统计模型让长度只能像「数据库数据变了查询性能就变」一样经验估算([0:14])
- 前缀复用(prefix reuse)：命中就能把 GPU 计算换成存储读取，常以延迟换成本，适合延迟容忍高的负载；用户只写几十 token 的 prompt、模型却观测到几千 token——复用率实际由 harness 等软件层掌控，可以做得聪明也可以很蠢，甚至「把用无节制的龙虾主题软件刷爆你缓存的用户 ban 掉」(原话如此)([0:16])

### 三、延迟预算、单副本基准与尾部延迟的直觉

- 两大延迟预算：TTFT(time to first token)与 TPOT/ITL(time per output token / inter-token latency)；TTLT(time to last token)因直接、痛苦地依赖输出长度，拆成「每 token 时间 × 输出长度」分别推理再组合；一旦上工具调用就天下大乱、只能回到线上经验数据；除批量数据处理外，一切按「单个用户/单个请求的体验」而非机器体验思考([0:17])
- 再按副本(per-replica)推理：从「一千并发用户每几秒一发」推总 QPS 只是聚合需求，实际要算「单副本在延迟预算与前缀复用约束下能装多少请求」再叠加副本数；与数据库不同(数据库尽量撑到 IPO 都不加副本)，推理各引擎天然相互独立(前缀缓存除外)，不必省着用副本([0:18])
- 三原型各有核心指标：chatbot plus 看交互性=每用户输出 tokens/s;background agent 看 time-to-last-token(PR、设计文档、生成图像交货那一刻);data processor 看每美元多少 mega token(吞吐按输入输出适当混合折算)([0:19])
- 单副本基准配方：最小延迟=串行发 n 条、记平均延迟的倒数；最大吞吐=一次全灌 n 条、记 n/总延迟(给引擎与硬件暴露最大并行度)；再扫描中间速率刻画行为；系统工程师可把这理解为测系统的脉冲响应——全灌总完成更快，但任一单请求延迟更高([0:21])
- 尾部直觉模拟器(Almanac 里的小工具)：保持 P50 不变、只拉高尾部——中位 token 1ms 就出来，画面却全是卡顿；P95/P99 看似只有 1/20、1/100 的用户碰上，但你测的是单序列/单 token 尺度，长尾实际主导体验；用过各家推理服务商的卡顿感正来源于此([0:23])

### 四、模型选择：效率约束 vs 能力约束

- 模型也是工作负载的一部分：该由应用开发者在 Jupyter 里跑 transformers 版本先定「要多聪明」，推理工程师再伺候它；两大家族约束——效率约束(efficiency bound)：智能够用、成本成主要驱动，开源模型主导；能力约束(capability bound)：当前最强智能都不够、某种程度上永远不够，专有厂商主打这里；类比：显示器刷新率 60Hz 够用、没人要 1000Hz(效率档)vs 内存 64GB 被 Claude Code 和 Chrome 吃光(能力档)；认为两者只剩一个会赢是愚蠢的([0:24])
- 能力档格局在变：专有模型仍主导，但开源微调正在追——前沿能力勉强够用的任务，对 DeepSeek V4 这类模型做 RL，能力反超还可能顺手更省；这波趋势是最近三到六个月才真正成真的([0:26])
- 效率档部署形态：典型单 GPU 单副本，1B/10B/50B 参数装进主流加速器显存；低延迟预算才上多 GPU(拆分到多条显存管道、消除延迟瓶颈)——而紧预算负载如今多是数据处理器与后台代理的 subagent，少见 chatbot plus；例外是语音代理：打电话的人不需要超级智能，100ms 内要回应；常见形态是多模态输入+结构化输出(非结构化→结构化不需要奥牌智力)；模型选择已挑花眼：Qwen(转写 Quinn)、Nemotron(转写 Nemo Tron)、GPT-OSS、Gemma、Step(StepFun)、Mistral，各有数据配比、尺寸与模态变体([0:28])
- 能力档部署形态：高智能眼下只有 scaling 一条路，只能靠变大——基本必然多 GPU 单副本(单芯片装不下万亿参数 MoE 的 HBM;Cerebras 那块大芯片除外，讲者当场记不清其 HBM 容量)，甚至跨节点多机；延迟预算越紧，计算与存储越要贴在一起；典型负载是 chatbot plus(ChatGPT/Claude 这类)与后台代理的 orchestrator([0:29])
- 多智能体编排与选型工具：后台代理常是多智能体系统——顶层 orchestrator 拿最高能力，下层 subagent 用更快更弱的模型干相似的活(与人类组织的相似性留作读者练习)；它们工具调用密集(智能不与世界交互还有什么用——迈克罗夫特·福尔摩斯 vs 夏洛克)，真做真观察→前缀命中率极高、工具延迟从毫秒跨到小时；自托管路径：应用常从专有 API 起步，想收回控制权时现实选项就是 DeepSeek、Kimi(转写 Kimmy)、GLM、MiniMax 各自最新模型；一旦微调，训练软件可移植性不如引擎、换模型锁得更死；选型「氛围检查」用 Artificial Analysis 的智能指数 × 每百万 token 价格图——自托管打平/打败该价格：中等难/难但非不可能，前提是负载能填满硬件([0:31])

### 五、推理引擎解剖与开源三强

- 推理引擎解剖：server 进程管对外通信，并控制 tokenization/detokenization——分词 CPU 密集、常开多进程；反解码(生成的 token 变回文本)来得慢、进程更少；中间是 CPU 上的调度器(scheduler)进程，定义并调度 GPU 上的全部工作——所有组件都重要，但要盯的瓶颈与关键在这里([0:33])
- GPU 是协处理器：你递交工作、它稍后交答案，目标是让它永远有活干——这正是 PyTorch 的道：「GPU 跑一个 petaflop 的时间，够 Python 慢悠悠决定下一个 kernel」；如今 CPU 与 GPU 之间的公共交换层/窄腰(narrow waist)就是 PyTorch([0:34])
- 开源三强：TRT-LLM——NVIDIA 独家开发、编译 C++ 运行时(部署后全 C++,天然绕开 CPU 瓶颈)，小模型小批量仍是最佳但非首选，投入似在下降(NVIDIA 一贯造软件示范硬件用法，等人接手再回去卖芯片)；vLLM——正牌开放治理(Linux Foundation 伞下，如 Postgres/PyTorch)，最先以开源开放治理身份上市、采用最广，带企业味；SGLang——开源但封闭治理(维护者组成的非营利持有、创始团队拆了初创)，性能至上的工程文化，Docker 镜像/分支版本「五十亿个」、各带微小优化，vLLM 则更多进 main；两者都干得好，尚未发现非选一个不可的理由——多一个追求者对使用者是好事([0:36])
- 学习路径：不必自写引擎，但要熟读——mini/nano vLLM 的极简实现帮你看懂架构；社区有很好的 vLLM 源码走读(讲者点名 Alexa Gaudich 版，人名按转写)；讲者把 disaggregated prefill/decode 做成 Modal 上的 notebook，可开多 GPU 跑；查代码用 Cognition 的 DeepWiki(不必在本地下载代码就能问「SGLang 的 radix cache 支不支持 hybrid 模型?讲者觉得不支持」,有图、有组织、可查询)；再加上自己的 agent 读源码——「用你自己的思考 token，别只花买来的」([0:38])

### 六、硬件与部署：脊点、GPU 选型、故障经济学与弹性

- 从硬件视角是两种负载：prefill 处理成百上千乃至数十万输入 token，要把数 GB 权重搬出显存进寄存器计算；decode 每出一个 token 都要重新把全部(激活)权重搬一遍——粗略规律：每 batch 元素(每 token 每请求)每字节只做约 2-3 次浮点运算(一次乘、一次累加)([0:40])
- 后果：decode 每字节只有个位数运算，而硬件趋势是脊点(ridge point)算术强度越抬越高——近期 NVIDIA tensor core 是每字节数百到上千 ops，内存带宽远追不上，于是加速器喂不饱、钱照花；所以 prefill 与 decode 要分开优化——这正是工作负载定义里两者分列的根源([0:42])
- 选型与替代品：目前唯一现实选项是 data center、Tensor Core、SXM 的近期 NVIDIA GPU——HBM 是焊死在基板上的片外内存(不是家里可插拔的 RAM)，超低延迟+超高带宽对 decode 是命根，还捎带更大容量；SXM 安装形态取代 PCIe 金手指，供电更足、散热更好，才能跑满瓦数(带宽与算力的天花板来自供电与排热)；节点间互联走 NVLink/InfiniBand；Tensor Core 本质是 GPU 里贴上去的 matmul ASIC(NVIDIA 在 Google 搞出 TPU 后补的，讲者自嘲此话会挑起争端)，承载当代硬件 99% 的 FLOPs、只会矩阵×矩阵——热提示：设计新架构务必能吃矩阵×矩阵，别犯「transformers 之误」让推理退化成矩阵×向量；书知识=讲者的 GPU Glossary(warp scheduler 到编译器 flag 一册收齐)，街知识=tensara.org(朋友做的 GPU 编程练习场，跑在 Modal 上)；CPU 缺 HBM、程序员控不了 L1/SM shared memory(模型变小、CPU 变大会交叉，但不是今天)；AMD 编程与满血性能仍难(watch this space)；TPU 与新推理芯片=端到端单一供应商、装机量小、缺「13 岁地下室黑客逆向指令集」的生态宽度——讲者枕下有块 2070、了如指掌，对 TPU 没有这种感情([0:46])
- 部署与故障经济学：部署选项被硬件锁死——GPU+HBM 稀缺且将长期稀缺，推理今天大多在数据中心替客户跑，本地/边缘化是 watch this space(类比:SQLite 有万亿个 vs Postgres)；云部署下网络先吃延迟预算：区域部署损几十 ms、全球部署损几百 ms，逼你走向区域化/边缘机房；硬件贵，养一台 8×B200 的成本是全场性能焦虑的隐形驱动；GPU 还爱坏——H100 平均无故障时间(MTTF)以天/周计(不是年)，老工程师的磁盘战争故事重演，必须默认故障、用冗余把硬件 fault 挡在系统 failure 之外；好在推理副本相互独立，路由换一个继续跑，不像训练必须全体在线；数千到低万卡规模的故障率因云厂商与部署而异(Modal 博客有战例)([0:50])
- 流量波动才是更大挑战：请求/分钟有季节性也有大摆动——史上增长最快的公司正被社媒以空前速度分发产品；推理不像训练可以围绕波动做工程计划，波动是「找上你」的；按峰值囤 GPU(买断或预留机架)=闲时照付租金/摊销，业界报出的利用率常见 30-40%；Modal 的答案是只开当下需要的量：常备空闲机器缓冲应对新流量(多租户下不知谁先扩，用运筹学/线性求解器按价格管缓冲大小)；文件系统懒加载+把 PyTorch/Python/OS 热文件与副本启动并发预取，存进从 Linux page cache 到 blob storage 的多级云缓存；应用启动(SGLang/vLLM 的 JIT 编译、CUDA graph capture、torch.compile)动辄数分钟——但「每个进程终究是数据结构」，用 CRIU、CUDA checkpoint 等快照恢复代替重新初始化(NVIDIA 也在即将发布的 Dynamo/GPU memory service 里做同类事)([0:53])

### 七、可观测性：三类 bug、日志纪律与评测

- 三类 bug 与可观测性定义：应用层 bug(与应用方共担，跨 ML、正确性与用户体验，基础设施工程师最躲得开)、模型质量 bug(部署时好好的、上线后变差——训练/服务偏斜;最常见是 tokenizer 与 chat template bug:特殊 token 与模板越来越复杂，开源模型首发几乎必带、随后慢慢被打磨——发现并修复它们是很有价值的开源贡献，「众人拾柴，连 tokenizer bug 也是浅的」)、性能 bug(随时间回归、异构环境下跨副本差异惊人)；可观测性=只靠日志就能定位并修复(Charity Majors:可观测性与可控性对偶，出自线性系统分析)——不搞最小复现也能 debug 分布式系统的愿景([0:57])
- 日志纪律与指标清单：模型质量侧——部署前先跑 evals 存基线，上线后激进记录 traces 与用户反馈，「求求你们把 token ID 也记进日志」(只记字符串，以后无法复现 token ID;Unicode 里极隐蔽的错在 token ID 里一目了然)；性能侧——宁多勿少，把「每种你想记的东西的最初始对象」记下来再过滤，总有一根冒烟的枪；常用指标：TTFT、TPOT/ITL、TTLT，RPS(用户级)与 QPS(模型级)分开定义，排队(从 GPU 的 SM 到 Kubernetes ingress 处处有队列，是尾部延迟主犯——TTFT/TTLT 飙升先查队列)，prefill/decode 分列计数与耗时，缓存命中率(进阶:把所有前缀永久落盘，离线算「无限缓存+完美探测」的理论最优命中率——「给自己立个毕生够不着的目标」)([1:00:00])
- 视角要全：per-replica 与聚合两层都要——聚合看整体分布、让副本与现状可比；median、tail、average 都记——均值用来算吞吐与 right-sizing，分位数才是用户体验；尾部看着只占 5%，时间上却是大头(呼应第三节的 token 时序模拟器)([1:02:00])
- evals：像测试一样吃力不讨好、难写、低地位劳动，但没它做不成应用——从装着一些 prompt 的 Jupyter/Excel 起步就有价值；做成模型无关，就能回答选哪个模型、跑在哪、能量化到多狠这类产品级决策；模型与部署都被证明是临时的，evals 是永恒的(至少要比模型活得久才能比出优劣)——微调、蒸馏、基准、无节制的有损优化、投机模型，全靠它把闸([1:03:00])
- 硬件层与一个实战案例：记温度、功耗、kernel 利用率(CUDA stream 上有活干的比率)——这些可异步、近零开销地测；更底层的性能计数器有额外开销、一般不可接受；Modal 内部 alpha 仪表盘上的多模态部署案例：P50 很平，P95/P99 却满是尖刺，且尖刺与排队时间在时间轴上相关——推断是请求生成到一半被引擎为公平分配 token 吞吐踢出去又换回来(推理引擎的公平调度行为)，对策是降低单副本并发或排查副本变慢；该部署场景是艺术展、性能可接受，就没有深挖([1:05:00])

### 八、性能优化与未来：投机解码、量化与 agent 时代

- 优化的优先级：最大的两件事是投机解码与量化——低垂果实但常是应用特定的，没法纯站巨人肩膀；然后是「在 host 而非 GPU 上做工」的中等收益苦活；最后才轮到 kernel 优化那种百分之几的提速——量大了才要紧，且要先摘完大果子([1:06:00])
- 投机解码：解决 decode 每字节运算太少(attention 里只有一两个 query 向量、MLP/MoE 里单 token)的问题——带宽跑满、flops 闲置，就让多余 flops 干「猜」的活：草稿猜出后续 token，想拿 token 的目标模型并行跑一遍，再用 Metropolis-Hastings 式拒绝采样保证输出分布与原模型完全一致(温度 0/greedy 即取最长一致前缀、首个分歧处用目标模型)；memory-bound(紧延迟预算+小模型上大 GPU)时是无脑必开，业界报 2x/4x/8x 的整数倍提速；同事 David Wang 称之「疯狂苦涩教训上头」(crazy bitter lesson pilled)——草稿模型本身也要训练、也随数据与算力变强([1:07:00])
- 草稿模型家族：用应用特定数据能把提速从 2x 拉到 6x(再 3 倍，常是「应用成不成立」的分水岭)；从 n-gram(复读 prompt 里见过的序列)到 MTP 多 token 预测——模型自带多个输出头、训练推理双收益(训练侧与推理侧两伙工程师罕见共赢)，渐成发布标配；更好做法是基于 hidden states 训草稿(哪怕用浅层——深层渐 specialize 于下一 token、浅层还握着「下一个想法」,见 model surgery 论文;MTP 不好用浅层、离线训练容易，EAGLE 是先驱)；Modal 押注 dFlash——类似 EAGLE 但用去噪扩散语言模型当草稿：扩散 LM 能力上限仍逊，但天然算术强度更高、没有 prefill/decode 分野、更贴硬件，正与作者合作改进并合入 SGLang([1:09:00])
- 量化：另一个最大杠杆——FP8→FP4 是 2x 提速，且内存受限与算力受限两边都吃(字节数减半;tensor core 的 OPS 按字节线性计)；难在「全栈协调」：FP4 硬件加速要 NVIDIA Blackwell；量化改变模型行为，必须应用层点头——evals、氛围检查、生产内测试就是应用层与硬件层的交接面；长序列更糟(精度低→累加多→误差累积)，短序列更有信心；FP8 已是标准(Hopper 起)，FP4 相对前沿、一般只做 MLP/MoE、不碰 attention(累加太多)；matmul 常是瓶颈，所以仍见近线性提速；KV cache 量化更难，最好训练时做(DeepSeek V4 的做法)——以上是截至本讲的现状，可能有遗漏的新论文([1:11:00])
- host 减负、kernel 与未来：别让 CPU 挡 GPU——CUDA graph capture 把海量 kernel 启动合并成一次(profiler 里一排 CUDA graphs 就是它)，引擎里务必打开；找 host 开销的免费仪器是功耗/温度(一个慢副本只画 2kW、本该 3kW+,用 Torch Profiler/Nsight Systems——同一套 CUDA Profiling Tools 接口——深挖，本周怀疑是 NUMA affinity 问题)；不必上来就高端：py-spy 看 host 就够，Modal 曾只用它给 SGLang 多模态推理提速 10%+(把每次请求重建的指针缓存进 Python dict)；kernel 已「接近光速」、高度可复用，只剩几个百分点，在乎百分比时再上 Nsight Compute 量算力/带宽利用率、对着汇编找流水线停顿——但高手写快 kernel 先用白板推瓶颈，再上经验工具；未来：有损怪招(跳层、剪枝、有损投机解码、为投机服务的 mega kernel)与覆盖特定层乃至整机的专用草稿；NVIDIA 下一代将出混装机架、内含 Groq 的 LPU(转写 Grok,按公司名应为 Groq)——眼下虽尚未对应 prefill/decode 分工，但讲者认为那只是历史惯性，未来两者将由不同加速器承担；软件工程越来越多的活是带 agent 干活：你的工作是搭「度量 agent 正确性」的系统(benchmark、配置、监控、接什么工具与 MCP)——毕竟还早没人敢把 AWS root 账号交给模型；vLLM/SGLang 建立在「造软件很贵」的假设上，若能为每个部署廉价定制引擎，那可能是更优策略(见 VibeServe 论文)；Modal 想要可扩展的工程系统，agent 是这个故事的一部分([1:14:00])

## 核心概念速查

| 术语 | 一句话解释 |
|---|---|
| Prefill / Decode | 推理两阶段：预填充处理整段输入(算术密集)，解码逐 token 生成(每字节仅约 2-3 次运算、内存带宽受限)，需分开优化 |
| TTFT / TPOT(ITL) | 首 token 时间与每输出 token 时间，两大延迟预算；TTLT≈TTFT+TPOT×输出长度，拆开推理再组合 |
| 效率约束 vs 能力约束(efficiency-/capability-bound) | 智能够用、成本主导(开源主导)vs 最强智能都不够、只能靠变大(专有主导)的两种工程约束 |
| 前缀复用(prefix reuse) | 相同前缀命中缓存，把 GPU 计算换成存储读取，以延迟换成本，复用率实际由 harness 软件层掌控 |
| 脊点(ridge point) | 算术强度拐点：超过它性能受内存带宽限制；decode 每字节个位数运算远低于 GPU 数百-上千 ops/字节的脊点 |
| 投机解码(speculative decoding) | 草稿猜 token+目标模型并行验证，Metropolis-Hastings 式拒绝采样保证分布不变，吃掉 decode 阶段闲置的 flops |
| MTP(multi-token prediction) | 模型自带多个输出头一次预测多 token，训练与推理双赢，渐成发布标配 |
| EAGLE / dFlash | 基于 hidden states/浅层训练草稿模型的先驱 / Modal 押注的扩散语言模型草稿(算术强度高、无 prefill/decode 分野) |
| CUDA Graph Capture | 把大量 CUDA kernel 启动合并为一次提交，消除 host 开销，推理引擎里务必打开 |
| CRIU / checkpoint-restore | 进程本质是数据结构：快照-恢复代替重新初始化，把数分钟的引擎启动压到秒级 |

## 自测题

1. 为什么说「训练是成本中心、推理是收入中心」?
   > 权重像「装软件的 CD」难以直接卖钱，必须围绕模型搭服务系统才有营收；营收再支撑继续训练，连投资人也要沿途看到营收；如今连 RL 后训练也依赖高效推理。
2. 三类 LLM 应用原型分别以什么指标为核心诉求?
   > chatbot plus 看每用户输出 tokens/s(交互性),background agent 看 time-to-last-token(交货那一刻),data processor 看每美元多少 mega token(吞吐)。
3. 单副本基准测试的两个极端怎么测?中间怎么办?
   > 最小延迟=串行发 n 条取平均延迟的倒数；最大吞吐=一次全灌 n 条取 n/总延迟；再在两者之间扫描请求速率刻画行为(即测系统脉冲响应)。
4. 为什么 decode 阶段天然喂不饱 GPU?由此推出什么工程结论?
   > 每字节只做约 2-3 次浮点运算，远低于 GPU 数百-上千 ops/字节的脊点，性能卡在内存带宽、钱照花；所以 prefill 与 decode 要分开优化。
5. 效率约束与能力约束两个 regime 里，开源与专有模型的格局有何不同?
   > 效率档智能够用、成本主导、开源模型主导；能力档最强智能都不够、专有主导——但开源微调+RL(如对 DeepSeek V4 做 RL)正把能力档也追上来。
6. 投机解码为什么能保证输出分布不变?什么场景「无脑必开」?
   > Metropolis-Hastings 式拒绝采样在数学上保证同分布(greedy 即取最长一致前缀);memory-bound(紧延迟预算+小模型上大 GPU)时闲置 flops 免费换速度，2x-8x。
7. 为什么 FP4 量化需要「全栈协调」?哪些层最敏感?
   > FP4 硬件加速要 Blackwell GPU、行为变化要应用层 evals 把关、长序列累加误差更糟；attention 因累加多通常不量化，一般只做 MLP/MoE。
8. Modal 让推理副本秒级启动的三招是什么?
   > 常备空闲机器缓冲、文件系统懒加载+热文件并发预取进多级云缓存、用 CRIU/CUDA checkpoint 快照恢复代替重新初始化(「进程终究是数据结构」)。
