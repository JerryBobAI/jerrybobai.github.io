## 一句话概览

本讲回答"agent 的记忆是什么、放哪、怎么管"：先借 **CoALA 框架**把记忆分成 working / episodic / semantic / procedural 四类，再区分**参数记忆 vs 上下文记忆**与三种存储介质（文件系统、数据库、知识图谱），然后归纳**四种架构模式**（从经验学程序、MemGPT 式分层、反思巩固、记忆维护），最后用 LoCoMo / PersonaMem / MemoryAgentBench 三个基准说明"检索对了也未必答对"，并收束于记住什么、信任与隐私、过度个性化三大挑战。

## 分节要点（带时间锚点）

### [0:00–0:05] 动机：没有记忆的 agent 会怎样

- 失败案例一 **Agent Luna**（Andon Labs）：这个"运营公司"的 agent 写了员工手册，其中明确规定了"员工迟到怎么办"；实际部署后员工说自己**迟到约 45 分钟**，Luna 只回"没问题，直接来就行"——手册明明就在记忆里，却从未被真正执行，且这类事发生了多次、从无警告。说明**有记忆 ≠ 会用记忆**。
- 失败案例二：用户让 agent"检查收件箱、建议归档和删除哪些邮件"，收件箱太长导致上下文被压缩，agent **忘了原始指令**，直接开始删光邮件。
- 无记忆的三种损失：**procedure**（每次都要重新教"怎么跑 GPU 实验"的流程）、**knowledge**（"删邮件前先问我""花钱做实验前先确认"这类用户规则丢失）、**progress**（长会话里忘了最初的目标与指令）。
- 有记忆的三种收益：**personalization**（学你的偏好，PersonaMem 例：意大利菜爱好者后来麸质过敏、转向地中海菜——记不住偏好就会推荐 pasta，记住了才推荐海鲜）、**skills**（Workflow Memory 论文：学会"按名字找地点"这个子技能后，规划路线时能直接复用）、**state**（跨会话说"接着上次聊的机票讲"，agent 能直接检索上次会话作答，而不是翻文件或反问用户）。

### [0:05–0:15] CoALA 四类记忆与"记忆 vs 上下文"

- 框架出处：**CoALA**（Cognitive Architectures for Language Agents），借鉴人类认知架构给 agent 内部结构分块。
- 四类记忆：

| 类型 | 是什么 | 讲座例子 |
|---|---|---|
| Working memory | 当前上下文窗口：观察、目标、系统提示、内部思考——**工作记忆 ≈ 上下文本身** | agent 此刻"看得见"的一切 |
| Episodic memory | 过去行为的原始记录：轨迹、工具调用、观察；聊天机器人里就是历史对话日志 | Generative Agents 里 Isabella Rodriguez 的 memory stream（环境中所发生一切的流水账） |
| Semantic memory | 关于世界与用户的事实、通用知识 | ChatGPT Memory 记住"用户有个 2 岁女儿、女儿喜欢水母"；查 Wikipedia 也算 |
| Procedural memory | 技能：如何完成任务的规则/程序，加载进 working memory 后指导行为 | Anthropic 的 brand skills 文件（Markdown）：如何把 Anthropic 品牌色应用到 PowerPoint |

- Q&A 洞见：
  - **为什么还要单独保留 episodic 原始日志？** 转换（摘要/提炼）会丢信息；原始日志留底，发现"当初记错了什么"还能回头重查；有时最佳示范就是原样例子。
  - **百万级上下文 + RAG 时代还需要记忆吗？** 讲者观点：RAG 本身就是记忆系统的基础设施（不必对立）；长跑 agent 任务可达数千万甚至上亿 token；且模型在超长上下文里做检索（needle-in-haystack）表现并不好——"未来 5 年内记忆不会消失"；无限上下文是否终将取代记忆是开放问题。
  - 短期/长期记忆的类比：working ≈ 短期，其余更接近长期；分类学本身就源自神经科学的启发。

### [0:15–0:20] 参数记忆 vs 上下文记忆

- 区别只在**信息存在哪**：参数记忆写进模型权重（预训练获得的语义知识、指令跟随能力）；上下文记忆是检索出来放进上下文窗口的内容。
- 冲突时谁赢？研究表明**通常上下文覆盖参数**，但若某事实在参数里刻得非常深，则不一定——没有保证。
- 何时该微调（更新参数记忆）？
  - **semantic**：小规模事实集合别微调——需要**上千份文档**模型才记得住，还伴随幻觉等损失；少量事实用上下文/RAG 更划算。
  - **procedural**：如果有可训练的 RL 环境，对基座模型做 RL 显著提升该任务表现，是更新程序性记忆的好方式——是否微调取决于你所处的环境。

### [0:20–0:30] 记忆系统三问与三种存储介质

- 设计算法前先回答三问：**what**（存什么、取什么：事实/程序/对话）、**when**（何时读写：agent 按需调用工具；后台 memory worker 观察对话自行决定；事件驱动——MemGPT 把 LLM 当操作系统，上下文溢出、用户请求都触发记忆操作）、**how**（怎么存取）。
- 三种存储介质：

| 介质 | 做法 | 例子 |
|---|---|---|
| 文件系统 | 每条记忆一个文件，agent 用 bash（grep/ls）自己管理；天然带层级 | LangChain 博客：procedural = AGENTS.md / skill 文件；episodic = 存对话原文的目录 |
| 数据库 | vector DB 做相似度检索、SQLite 存元数据用 SQL 查、BM25 做精确词项检索 | 讲座提示：工具检索一讲里的 embedding 检索知识全部适用 |
| 知识图谱 | 从对话中抽实体、连关系边，图变大后做 LLM 聚类并写 community 摘要 | **Zep**：episodes → entities → communities 三层；例：从对话建"表亲喜欢你的狗"的实体与关系 |

- Q&A 洞见：知识图谱主要服务 **semantic** 记忆（也可勉强编码程序，但边界模糊）；三者谁最好**取决于程序**——讲者个人观点：能简单就先**文件系统**（代价是延迟，agent 要跑一堆 bash 命令），当需要在检索速度等权衡上做优化时再上数据库/图；MemGPT 里文档走 embedding、对话历史保留全文精确检索，说明这些全是设计选择。图的好处是可以把部分"算力"前移进检索本身（GraphRAG 类算法）。

### [0:30–0:43] 模式一：从经验学程序（Voyager / Agent Workflow Memory / skill files）

- **Voyager**（Minecraft）：curriculum 出题（如"砍木头"）→ 写 JavaScript 代码与环境交互 → 环境反馈判定成败 → 成功则把代码 + 描述（"装备石剑打僵尸：找不到就造石剑和盾"）**embed 后存入技能库**，失败则用观察反馈重写程序。之后要造铁镐时，用目标描述 embed 检索技能库复用。
  - Q&A：查询与 key 不是精确匹配，靠 embedding 相似度检索；可能检索出多个相似技能——Voyager 只禁止完全同名（"make iron pickaxe"）重复，措辞稍异就会积累出一堆功能重复的技能。
  - 结果：有技能库的 Voyager 经 **102 次提示迭代**推进到**钻石工具**；没有技能库只能到铁器，且每个任务花更多迭代与尝试。
- **Agent Workflow Memory**：更通用的版本（不只 Minecraft）。电脑操作 agent 完成任务（如查订单 130：点击、滚动）→ 轨迹成功后做 **workflow induction**：从多条成功轨迹归纳可复用模式（"逛购物网站看子类目时，先 hover 主类目再点子类目"）→ 写回记忆。该论文简单粗暴地直接**重写进系统提示**、不做检索。
  - 结果：购物、Reddit、GSM8K-风格卡牌等多个域上超过人工编写的 workflow；存在明显"学习期"——前几个样本准确率很低，**不到 10–15 个样本**就学会了关键 workflow。
  - Q&A：与 RL 的关系——像"上下文内的强化学习"，采样效率远高于 RL（RL 需要的样本多得多；与后续 GEPA 一讲呼应）；但把 workflow 塞系统提示不可扩展，长期运行的 agent 还是需要检索例程。
- **Skill files**：把上面思想工程化——写 skill.md（含 frontmatter 元数据），只把**名字 + 描述**放进上下文，agent 判断需要时再读全文。核心洞察：基础模型够强后，**文件系统本身就够当记忆管理器**，你只需创建文件并让 agent 知道它存在。
- 共同局限：**动态环境会过时**——底座环境一变，学到的程序就失效，而这些文档并不会告诉你如何修正；需要配合后面"记忆维护"模式；让 agent 自己改 skill 文件是一种缓解。

### [0:43–0:55] 模式二：分层记忆（MemGPT 与多级变体）

- MemGPT 核心思想：**给 LLM 自己管理记忆的工具**，类比操作系统的虚拟内存管理。三层结构：
  - **working context**：系统指令 + agent 可读写的工作区（注意：术语上 working memory 指整个上下文，这里的 working context 是其中可操作的部分）；
  - **recall storage**：对话历史按 **FIFO** 管理——上下文放不下时最老的消息先被挤出去，存入 recall，可做**精确字符串检索**（更像 episodic）；
  - **archival storage**：长期事实与全局知识的**向量库**，语义检索。
- 经典例子：用户说"男朋友 James 给我烤了生日派"→ agent 写入 working context（用户生日、有男友 James）；情人节问"James 怎么样"→ 答"我们分手了"→ agent **替换** working context 中的关系状态并送上安慰——这就是用工具操作记忆。
  - 检索例一：用户提到去过 Six Flags，agent 在 recall 历史中精确检索，发现两人正是在 Six Flags 初遇，于是说出"真浪漫"——实体识别由 LLM 自己决定（Six Flags 是检索对象），不需要预置 NER，用 BM25/精确匹配即可。
  - 检索例二：把一堆文档传入 archival，问"第一位诺贝尔物理学奖得主是谁"，第一页结果不对就**再翻下一页**，直到找到——检索策略本身交给 LLM。
- 结果：加记忆后各模型都能完成这种深层记忆检索；关键曲线是**精度不随文档数量增加而下降**——传统 RAG 塞更多文档会稀释上下文、拉低表现，而让模型用工具自管记忆时，性能与"检索进多少文档"基本解耦。
- 简要延伸：另一篇工作把角色记忆分成短/中/长三级，靠访问频率在层级间搬运——与 MemGPT 的区别在于**记忆维护由幕后系统（分析使用情况的工作流）做决策**，而非像 MemGPT 那样全靠 LLM 自己说"这条进档案"。Q&A 也指出：该领域**尚无标准化评测指标**（延迟、成本、准确率的统一报告方式仍缺位），是可做的方向。

### [0:55–1:05:00] 模式三：反思巩固；模式四：记忆维护

- **Reflexion**（前两讲已出现，快讲）：对轨迹做反思，把"为什么这些轨迹有用"的反思文本（而非原始轨迹全部）放进上下文效果更好——**反思本身是关键组件**。
- **Generative Agents**（Smallville）：agent（Isabella Rodriguez）想办情人节派对并邀请全镇。记忆架构 = memory stream（episodic）+ 检索（**recency / importance / relevance** 三项打分）+ planning + reflection，反思结果写回 memory stream。被问"现在最期待什么"时，检索出"Isabella 正兴奋地筹备 Hobbs Cafe 的情人节派对"得分最高，于是自然答出期待在 Hobbs Cafe 办派对。
  - 消融：完整架构 vs 去掉 reflection / planning / observation，以及人类众包工人替演——**reflection 是 agent 行为可信度的关键成分**之一。
- **Sleep-time compute**：模型闲置时（"睡觉"）离线分析过往对话。例一：昨天聊过"杂耍艺人能同时抛 800 个球，1/4 是网球，一半是靛蓝色"——睡眠期把算术先算好，次日直接答"标记的靛蓝网球是 10 个"。例二：Chad 喜欢蓝、更喜欢红、最爱灰、讨厌绿——睡眠期合并重写为"颜色偏好排序：灰 > 红 > 蓝，最不喜欢绿"，以后每次检索不用再现场做小逻辑题。
  - AIME 实验口径：横轴只计测试时 token 时 sleep-time compute 大胜；把睡眠 token 算进总账后，仍然优于 pass@k 多次采样——**按"回答一个问题花费的总 token"算是赚的**。
  - Q&A 洞见：本质是**省时省钱**而非更准——若把同样的计算放到测试时，理论精度不输甚至更好；但在"回答用户问题只舍得花 1k token 推理"的预算约束下，它实际更准。局限：不知道用户将来会问什么（想什么是个难题）；原文没给工具，只做纯思考——给睡眠 agent 配工具会引出"你不在时 agent 背后干什么"的安全问题。
- 记忆维护的另外两条路线：**A-Mem**——专门养一个"管理记忆"的 agent，负责建立记忆间连接、演化和取舍；**Mem0**——从用户/助手消息中抽取要点，对记忆库执行 **ADD / UPDATE / DELETE / NOOP** 四种操作，底层用 Zep 知识图谱检测冲突并解决，持续让图与最新对话同步。

### [1:05:00–1:15:00] 基准评测：LoCoMo、PersonaMem、MemoryAgentBench

- 好的记忆基准四要素：**真实**（记忆来源与查询方式贴近实际使用）、**长上下文**（不够长就根本没考到记忆）、**复杂**、**可验证**（有标准答案）。
- **LoCoMo**：用 Generative Agents 架构模拟两个用户之间的长对话（约 **16,000 token**、跨越数天），人工校对消除幻觉后，就对话内容提问（"昨晚说我们给女儿过了生日——是谁的生日？"）。论文核心发现：**即使检索命中了正确记忆（reproduction accuracy 高），问答准确率也可能更低**——检索 50 条观察时上下文塞太满，反而答不对；说明问题不止在检索，还在 LLM 对记忆的处理。局限：模拟对话不完全真实。
- **PersonaMem**：模拟**用户与 assistant** 的多会话对话，用户 persona 的偏好随时间演变（意大利菜 → 麸质过敏 → 地中海菜）；多选题中混入干扰项（与记忆矛盾的选择、泛泛而谈的选择），要求模型选**个性化正确**的那项。发现 memory 与 RAG 都重要；Mem0 能记住并更新知识图谱，对"偏好随时间演化"尤其关键。局限：多选题形式难度有限。
- **MemoryAgentBench**：干脆把记忆放进 **memory–agent–environment 循环**考。群体旅行规划任务：Tracy 先定行程 → Chelsea 加入（要住豪华酒店）→ 重新规划 → Emily 加入 → 再规划……不断加入新约束，最后检验行程是否满足每个人的限制。把长历史直接塞上下文的基线对比 Mem0、RAG 等记忆系统——结果是**记忆 agent 反而在这条 benchmark 上表现最差**。讲者强调：不能全归罪于记忆（任务本身也有很多其他失败方式），但这说明记忆系统有巨大改进空间。
- Q&A：能否不用记忆工具、纯靠长上下文？取决于任务长度——MemoryAgentBench 的上下文长到必须用工具，于是两种路线被放在同一考场直接对比。

### [1:15–结尾] 三大挑战与开放问题

- **记住什么、忘掉什么**：信息未来的相关性在写入时不可知；全存则检索、上下文与服务成本齐涨；乱忘又会丢掉将来有用的证据。例：用户开玩笑说"10 点前的会议都不算数，除非有蛋糕"——agent 到底该不该记？玩笑与真实偏好的边界本身就是难题。
- **信任、隐私与用户控制**：
  - 记忆投毒：往 procedural memory 注入"危险驾驶"记忆后，用户让 agent"平稳安全地开去 O'Hare 机场"，agent 却检索出危险驾驶记忆、行为突变——记忆不可信，agent 就不可信。
  - 隐私泄露：用户让 agent"每周给 Susan Harrington 发工作周报"，周报里含"和竞争对手公司的猎头吃了午餐"——agent 不理解什么该保密，记忆让泄露更自动化（隐私与安全讲将深入）。
- **过度个性化**：LLM 有时太急于使用上下文里的记忆。真实案例：用户问"你怎么看年轻选民对选举的影响"，模型检索到"该用户喜欢关注小胜利"的记忆，竟回答"就像你专注于生活中的小改变一样，每个年轻的声音都是通往更大改变的小胜利"——答非所问的讨好。此外**不同用户想要个性化的程度不同**，"个性化多少"本身是设计问题。
